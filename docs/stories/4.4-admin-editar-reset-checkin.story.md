# Story 4.4 — Admin: editar cadastro do atleta e refazer check-in

**Status:** Done
**Autorização:** proposta apresentada em 03/11/2026 (artefato “Proposta Check-in 2026”) e aprovada pelo usuário no mesmo dia.
**Decisões do usuário (03/11/2026):**
- D2: ao refazer o check-in, o termo anterior é arquivado (nunca apagado).
- D3: o atleta é avisado por e-mail quando o check-in é refeito (opção marcada por padrão).
- D5: só o administrador (conta admin) edita e refaz check-in.
**Origem:** Story 4.2 (documentos no dashboard); item “reabrir check-in” do “Fora do escopo” da Story 4.1.

## Problema

Erros de cadastro vindos da planilha (nome, e-mail, equipe, categoria) só podem ser corrigidos na planilha, e a reimportação sobrescreve qualquer ajuste manual. Um check-in feito com dados ou documentos errados não pode ser refeito.

## Escopo

**Dentro:** editar cadastro em `/admin/documentos/[id]`; refazer check-in com arquivo do termo anterior; histórico de alterações; importação preservando as correções; selo na listagem.
**Fora:** alterar o tipo da inscrição (dupla/individual), criar ou excluir atletas, editar o termo assinado.

## Acceptance Criteria

- [x] Página do atleta mostra o cadastro (nome, Instagram, camisa, e-mail e telefone da inscrição, equipe, box, competição, categoria e situação).
- [x] “Editar cadastro” abre um painel lateral com esses campos; campos da inscrição avisam que valem para a dupla; o tipo dupla/individual não é editável.
- [x] Validação por campo (nome, equipe e categoria obrigatórios; e-mail válido; competição e situação da lista) com mensagens em português.
- [x] Atleta já confirmado: o painel avisa que o termo assinado mantém os dados da assinatura.
- [x] Trocar o e-mail da inscrição encerra códigos e sessões do e-mail antigo.
- [x] Toda edição grava no histórico quem fez, quando e o valor antes e depois; a página do atleta mostra o histórico.
- [x] Campos editados no painel ficam marcados e `npm run athletes:import` não os sobrescreve (avisa no terminal o que foi preservado); situação editada também não é alterada pela regra “não está mais na planilha”.
- [x] “Refazer check-in” em área separada, com confirmação na própria página, motivo obrigatório (dados do cadastro, atestado, assinatura/PAR-Q, outro com texto) e “Avisar o atleta por e-mail” marcado por padrão.
- [x] Ao refazer: o termo, as respostas e os caminhos da assinatura e do atestado vão para o arquivo (arquivos mantidos no Storage); o atleta volta a “Pendente”; a barra pública diminui; o histórico registra o motivo.
- [x] E-mail ao atleta (e-mail da inscrição) explica que o check-in foi reaberto, o motivo e o link para `/check-in`.
- [x] Página do atleta lista os termos arquivados (assinado em, arquivado em, motivo, por quem); a listagem de Documentos mostra o selo “Check-in reaberto” para pendentes com termo arquivado.
- [x] Só admin ativo: as funções do banco recusam quem não é admin e as Server Actions conferem o perfil.
- [x] Testes: funções do banco (PGlite: permissões, edição, histórico, reset e arquivo), validação do formulário, textos do histórico e e-mail; `npm run lint`, `npm run typecheck`, `npm test` e `npm run build`.

- Reset por engano: confirmação com motivo e termo arquivado, recuperável pelo histórico.

## Dev Notes

- As funções do banco rodam com a sessão do admin (`is_admin()` + registro de quem fez); as Server Actions conferem o perfil antes.
- O termo arquivado guarda a linha inteira de `athlete_checkins` em JSON, então novas colunas do termo entram no arquivo sem mudar a tabela.
- Página do atleta funciona sem a migration 4.4 (mostra o aviso para rodar `npm run db:push` e esconde editar/refazer).
- Verificado com `next start` contra o Supabase local, Chrome headless em 1280 px e um receptor local no lugar do Resend: validação do e-mail; edição de nome, e-mail e categoria com selos “Corrigido no painel” e histórico; reset sem motivo bloqueado; reset com motivo → termo arquivado, atleta pendente, aviso e e-mail com o motivo para o novo endereço; selo na listagem. Importação com planilha sintética: nome, categoria e situação corrigidos foram preservados e listados no terminal.
- Dados de teste removidos do banco local depois da verificação.
- Observação fora do escopo: no Supabase local recente, `authenticated` não tem `SELECT` em `profiles` (a migration inicial depende das permissões automáticas dos projetos antigos). Em um projeto Supabase novo o login do admin falharia; vale uma migration com `grant select on public.profiles to authenticated`.
- Quality gates: `npm run lint` ok, `npm run typecheck` ok, `npm test` 347/347, `npm run build` ok.
