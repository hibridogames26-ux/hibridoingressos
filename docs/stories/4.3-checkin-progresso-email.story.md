# Story 4.3 — Check-in público: barra de progresso e entrada pelo e-mail da inscrição

**Status:** Done
**Autorização:** proposta apresentada em 03/11/2026 (artefato “Proposta Check-in 2026”) e aprovada pelo usuário no mesmo dia.
**Decisões do usuário (03/11/2026):**
- D1: opção B — a página pública mostra só o progresso; o atleta entra pelo e-mail da inscrição.
- D4: quando o e-mail não tiver inscrição, dizer claramente e recomendar contato com a organização do evento.
**Origem:** Story 4.1 (painel público com a lista de atletas).

## Problema

`/check-in` lista todos os atletas aprovados com nome, equipe, box e situação. Qualquer pessoa com o link vê quem está pendente, o que vai contra o princípio “o que é público é o mínimo para orientar” (PRODUCT.md). A identidade já é confirmada pelo código no e-mail da inscrição, então a lista não protege nada.

## Escopo

**Dentro:** barra de progresso agregada; entrada por e-mail → código → escolha do atleta; sessão por e-mail; página do atleta passa a exigir essa sessão.
**Fora:** mudanças no formulário do termo, no PAR-Q, no upload do atestado e no painel administrativo (Story 4.4).

## Acceptance Criteria

- [x] `/check-in` não envia ao navegador nenhum nome, equipe ou box: só os totais (com check-in, total e por competição).
- [x] Barra de progresso mostra “X de Y atletas com check-in” e “Faltam N atletas para fechar o check-in”; com 100% mostra “Todos os atletas fizeram check-in”; divisão por competição só quando houver mais de uma; atualiza sozinha a cada 60 s; texto acessível para leitor de tela; animação respeita “reduzir movimento”.
- [x] Entrada pelo e-mail da inscrição: o atleta digita o e-mail e recebe um código de 6 dígitos (válido por 10 min, até 5 tentativas, reenvio após 60 s, até 5 envios por hora por e-mail; até 10 e-mails não encontrados por hora por IP).
- [x] E-mail sem inscrição aprovada: mensagem clara (“Não encontramos inscrição com este e-mail”) com a recomendação de conferir o e-mail usado e falar com a organização do evento.
- [x] Todos os atletas do e-mail já confirmados: mensagem informando que o check-in está completo.
- [x] Código correto abre uma sessão de 2 h (cookie httpOnly) e mostra “Quem vai fazer o check-in?” com os atletas das inscrições daquele e-mail (dupla: os dois), cada um com a situação.
- [x] `/check-in/[id]` sem sessão do e-mail daquele atleta redireciona para `/check-in`; atleta já confirmado continua mostrando a confirmação.
- [x] Depois de enviar o termo, a sessão continua valendo para o outro integrante da dupla no mesmo aparelho.
- [x] “Usar outro e-mail” encerra a sessão.
- [x] Mudança do e-mail da inscrição no admin (Story 4.4) encerra o acesso do e-mail antigo àquela inscrição.
- [x] Testes: funções do banco (PGlite) e regras de progresso; `npm run lint`, `npm run typecheck`, `npm test` e `npm run build`.

## Riscos

- Atleta que não lembra o e-mail da inscrição fica travado: mitigado pela mensagem com orientação e pela edição do e-mail no admin (Story 4.4).
- Consulta de e-mails inscritos (enumeração): mitigada pelo limite por IP e por e-mail.

## Dev Notes

- O código e a sessão passam a ser por e-mail (não por atleta). O acesso de uma sessão a um atleta é conferido a cada requisição contra o e-mail **atual** da inscrição, então trocar o e-mail no admin encerra o acesso do antigo sem precisar apagar sessões.
- O limite por IP conta só e-mails não encontrados (consulta de quem está inscrito). Contar todas as consultas bloquearia atletas na mesma rede do box.
- As tabelas e funções do código por atleta da Story 4.1 (`athlete_checkin_codes`, `issue_checkin_code`, `verify_checkin_code`) continuam no banco, sem uso no app.
- Verificado com `next start` contra o Supabase local (dados da 4.1), Chrome headless em 390 px e 1280 px, e um receptor local no lugar do Resend (nenhum e-mail saiu): o HTML de `/check-in` não contém nenhum dos 180 nomes, equipes ou boxes; e-mail não encontrado; código enviado (assunto e atletas conferidos); código errado; código certo → escolha do atleta → formulário; outro aparelho sem sessão → 307 para `/check-in`; sessão do e-mail antigo depois da troca no admin → volta à etapa do e-mail.
- Não refeito no navegador: o envio completo do termo (assinatura e upload do atestado). A única mudança nesse caminho é a checagem de sessão, coberta pelo typecheck; o formulário abrir com a sessão e a recusa sem sessão foram conferidos no navegador.
- Quality gates: `npm run lint` ok, `npm run typecheck` ok, `npm test` 347/347, `npm run build` ok.
